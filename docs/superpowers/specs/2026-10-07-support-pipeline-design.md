# ZainCash Support Pipeline Automation — Design Spec

- **Hackathon:** Agentic AI Challenge Iraq, Topic 06 "Support Pipeline Automation"
- **Date:** 2026-10-07
- **Status:** Draft, awaiting review
- **Team:** 2–4 people, build window of 1–2 weeks

---

## 1. Goal and success criteria

The goal is a back-office **batch pipeline**, not a chatbot. For each Iraqi-dialect support ticket in a queue, it:

1. classifies the issue,
2. sets a priority,
3. extracts the transaction reference, amount, date and phone number,
4. checks those details against a mock transaction store,
5. routes the ticket to a team,
6. drafts a grounded Iraqi-Arabic reply for a person to approve.

Anything the pipeline is unsure about is escalated with a note. Nothing is ever sent automatically.

### Requirements from the brief

| Brief requirement | How the design meets it |
|---|---|
| Runs over a batch and summarises what it did | `runner.py` produces a run summary (§6.8). The UI Runs page shows it. |
| Every classification carries a confidence; low-confidence tickets are escalated | Jev's calibrated confidence, the cascade to Gemini self-consistency, and escalation rules (§6.2, §6.4) |
| Drafts are never sent automatically | There is no send path anywhere in the code. The reviewer approves, edits or rejects (§6.7, §8). |
| Measured on a labelled test set the pipeline was not tuned on | A 100-ticket test split, with its hash committed before tuning starts (§7) |
| At least 200 synthetic Iraqi-dialect tickets | About 300 generated tickets (§7.1) |
| Classification and extraction accuracy, with the confusion cases discussed | The evaluation suite (§7.3) |
| Drafts an agent would send with minor edits | Grounded RAG drafting, guardrails, LLM-judge scores, human ratings and edit distance (§6.5–6.6, §7.3) |
| Throughput view | Run summary and Eval page |
| Stretch goal: weekly pattern report | In scope (§9) |

### Rules that apply to every topic

- Iraqi Arabic is the default language.
- All data is synthetic and generated by an LLM.
- Everything used is disclosed.
- At least 3 failure modes are documented.
- The system runs live on input the judges supply.
- The repo has commit history spanning the build period.
- Simple and reliable beats complex.

### What counts as success

- It runs live on judge input through the UI ("Try a ticket" page, CSV/JSON upload) and the CLI.
- Test-set results are committed for three modes: `jev`, `gemini` and `cascade`.
- The four pre-scoring checks are passed: commit history, live run, disclosure, and failure modes.

### Out of scope

- A customer-facing chatbot.
- Real customer data.
- Real ZainCash integrations.
- Sending messages.
- Cloud deployment (runs locally only).
- User-research interviews. The team chose to skip these, which is a known scoring gap.

## 2. Key decisions

| Topic | Decision |
|---|---|
| Existing chatbot code (`src/customer_support/` LangGraph warranty bot) | **Removed completely.** Replaced by the new monorepo layout. |
| Pipeline style | **A fixed sequence of stages.** Classification, extraction, routing and escalation are deterministic and use Jev plus code. A **bounded LangChain tool-calling agent** is used only for the investigate-and-draft stage. |
| Classifier | **A cascade.** Jev (TypeSafe System One) runs first. When it isn't confident, Gemini with self-consistency gives a second opinion. If that is still uncertain, the ticket goes to a person. |
| Generative LLM | Google Gemini: `gemini-2.5-flash` for the pipeline and `gemini-2.5-pro` for generating data and for the LLM judge |
| Embeddings | `gemini-embedding-001` with `output_dimensionality=768` |
| Backend | Python 3.11, `uv`, FastAPI, SQLAlchemy 2, Alembic, LangChain 1.x |
| Frontend | React + Vite + TypeScript, Tailwind, TanStack Query, React Router |
| Storage | Postgres 16 with the pgvector extension |
| Runtime | Local `docker compose up`: three services (db, backend, frontend) |
| Knowledge base | Staff upload policy and FAQ documents (PDF, MD, TXT). They are chunked, embedded and stored in pgvector. Drafts cite chunk IDs. |
| Ticket input | Paste one ticket in the UI, upload a CSV/JSON batch, or run the CLI. All three use the same pipeline code. |
| Languages | Drafts are in Iraqi Arabic. The UI is in English, with ticket and draft text shown right-to-left. |
| Dataset | About 300 tickets: 200 dev and 100 held-out test |

## 4. Taxonomy (`data/taxonomy.yaml`)

The taxonomy file is the single source of truth for categories, teams and priorities. Each category has these fields:

- `id`
- `team`
- `what`, a description in English and Iraqi Arabic
- `not_for`, which says what the category does not cover
- 2 to 3 Iraqi-dialect `examples`
- `required_fields`, the fields a ticket of this category should contain
- `min_priority`

| Category | Team |
|---|---|
| failed_transfer | Payments Ops |
| wrong_recipient | Disputes |
| login_access | Account & Security |
| agent_dispute | Agent Network |
| card_issue | Cards |
| bill_payment | Payments Ops |
| account_kyc | Account & Security |
| refund_request | Disputes |
| fraud_report | Account & Security (fraud desk) |
| app_bug | Tech Support |
| general_inquiry | General Care |
| other | General Care |

**Priorities:**
- P1: money at risk now or fraud
- P2: money lost or stuck
- P3: service blocked, no money involved
- P4: information request

**Hard overrides:**
- `fraud_suspected` above 0.5 sets the priority to P1.
- `money_lost` above 0.5 sets the priority to at least P2.

## 6. Pipeline: how each ticket is processed

### 6.1 Normalize (code)

- Unify Arabic letter variants: أ, إ and آ become ا; ى becomes ي. Also strip tatweel (ـ) and diacritics.
- Convert Arabic-Indic digits (٠–٩) and Persian digits (۰–۹) to ASCII digits.
- Detect Arabizi (Arabic written in Latin letters) and mixed English, and record the result as metadata.
- Mask card numbers.
- Keep the original text for display. Both the original and the normalised text are passed to later stages.

### 6.2 Classify (cascade)

**State sent to Jev:** `{ticket_text, normalized_text, channel, received_at}`. It contains only what the questions need.

**One `AsyncTypeSafeClient.system_one` call (pinned to `jev-1.13.0`) asks:**

- **Choice `category`.** The criteria are the structured `{what, not_for, examples}` entries from the taxonomy, plus `other`.
- **Score `priority`.** Four levels, each with a structured description.
- **Nouls:**
  - `fraud_suspected`
  - `money_lost`
  - `multi_issue`
  - `urgent_or_angry`
  - `mentions_specific_transaction`
  - `asks_for_human`
- **Extraction picks** (see §6.3). These go in the same call.

**Option-order check:** a second Jev call asks only the category Choice, with the options in reversed order. This addresses the documented bias toward the first option. If the two calls give different top labels, the ticket is treated as uncertain.

**When Jev's answer counts as confident:** all three must hold:
- top probability ≥ 0.60
- `confidence` ≥ `T_JEV` (starts at 0.6, tuned on dev only)
- the order check agrees

If any of these fails, the Gemini fallback runs.

**Gemini fallback:**
- `gemini-2.5-flash` with structured output (a Pydantic schema), n=3 samples at temperature 0.7.
- Its confidence is the share of samples that agree with the majority label.
- If confidence < `T_GEM` (starts at 0.67), the ticket is escalated with reason `low_confidence`.
- If Gemini is confident but disagrees with a Jev answer whose confidence was at least 0.4, the ticket is escalated with reason `classifier_disagreement`.
- Otherwise the Gemini label is used, with `classifier_path = gemini_fallback`.

**Modes**

| Mode | Classification | Extraction |
|---|---|---|
| `jev` | Jev only (never Gemini) | Jev picks; Gemini as the fallback described in §6.3 |
| `gemini` | Gemini only (no Jev calls) | Gemini only |
| `cascade` | As described above | As in §6.3 |

All three modes share everything else, including the drafting agent and the guardrails.

The Jev credential-request check in §6.6 runs in every mode. When the run is degraded (Jev unavailable), that check falls back to the regex only, and this is recorded in the run summary.

### 6.3 Extract

1. **`candidates.py` finds candidates with regex**, tuned to over-collect:
   - transaction references, for example `ZC\d{10}`, including variants with spaces or dashes
   - amounts: digits, with الف/ألف/k/مليون/دينار/IQD/$
   - phone numbers: `07[3-9]\d{8}` and `+9647…`
   - date phrases: absolute dates, and relative ones like امس, اليوم, قبل يومين, الاسبوع الماضي
2. **For each field, a Jev Choice in the §6.2 call picks one candidate or `none`.** The value is copied exactly from the ticket and cannot be invented. A Choice can have at most 255 options; candidate lists are truncated to stay under that.
3. **Gemini fallback** runs only when a field has no candidates but the text seems to contain it (for example amounts written in words such as "خمسين الف"), or when the Jev pick has confidence below 0.5. Gemini returns `{value, verbatim_span}`. Code checks that `verbatim_span` really occurs in the text. If it doesn't, the value is set to `null`.
4. **Dates:** relative dates are resolved in code against `received_at`.
5. **The rule:** a field that wasn't stated in the ticket is always `null`. A value is never filled in by guessing.

### 6.4 Rules (code)

1. **Team:** comes from `taxonomy.yaml` for the category.
2. **Priority:** the Jev Score is used, then the hard overrides from §4 and the category's `min_priority` are applied.
3. **Lookup (`lookup.py`):**
   - If there is a transaction reference, look it up exactly.
   - Otherwise search by phone number, amount within ±1%, and a ±3-day window around the date.
   - The result is `lookup_status`, as listed in §5.
4. **Escalation reasons** (a list; any one of them means the ticket is escalated):
   - `fraud_suspected`
   - `multi_issue`
   - `low_confidence`
   - `classifier_disagreement`
   - `missing_required_fields`
   - `txn_not_found`
   - `amount_mismatch`
   - `asks_for_human`
5. Whenever a ticket is escalated, the system writes a one-line note for the reviewer.

### 6.5 Investigate and draft (a bounded LangChain agent)

**Model and limits:**
- `gemini-2.5-flash` via `langchain-google-genai` and `create_agent`
- at most 6 tool calls
- a 30-second timeout
- the agent must finish by calling `submit_draft`

**Context the agent receives:**
- the ticket, wrapped in a `<ticket>` block. The system prompt says it is untrusted data, never instructions.
- the classification and extracted fields
- the lookup result
- the team

**Tools (`pipeline/tools/`).** They only read data, apart from the two tools that record the agent's own output:

| # | Tool | Purpose |
|---|---|---|
| 1 | `lookup_transaction(txn_ref)` | Look up a transaction by its exact reference |
| 2 | `search_transactions(phone, amount_iqd?, date_from, date_to)` | Fuzzy search for when there's no reference. Returns at most 10. |
| 3 | `get_customer_recent_transactions(phone, days=14)` | Context for the customer's recent activity |
| 4 | `get_customer_ticket_history(phone, days=30)` | Spot repeat contacts and unresolved earlier tickets |
| 5 | `check_service_status(service, at_time)` | Check for known incidents and outages |
| 6 | `search_knowledge_base(query, category?, k=5)` | pgvector top-k chunks with their IDs |
| 7 | `flag_for_human(reason, note)` | Adds an escalation reason, for example `no_kb_support` |
| 8 | `submit_draft(reply_ar, citations[], used_txn_ref?, internal_note)` | The final step. It records the draft. |

Every tool call, with its arguments and result, is saved to `agent_trace`.

### 6.6 Draft guardrails (code + Jev)

1. Every citation ID must be a chunk the agent actually retrieved in this run, and there must be at least one citation.
2. Every amount, transaction reference, date and phone number in the draft must appear in the ticket or in the matched transaction.
3. The draft must not ask for an OTP, PIN or password. This is checked two ways:
   - an Arabic and English regex
   - a Jev `requests_credentials` Noul, which must be below 0.2
4. The draft must be in Arabic script, and at most 120 words.

If a check fails, the draft is kept but marked. The ticket is escalated with reason `draft_failed_guardrail`, and the note says which check failed.

### 6.7 Persist

- The result is saved with status `pending_review` or `escalated`.
- **There is no send path anywhere.**
- Review actions write to `reviews`.
- An approved reply is available through "Copy approved reply" only.

### 6.8 Running a batch and the run summary

- **Background task:** batches run as a FastAPI background task, or synchronously from the CLI.
- **Concurrency:** an `asyncio.Semaphore` limits concurrency to 20.
- **Failures:** each ticket is processed on its own. A ticket gets 2 retries with backoff, then is marked `failed`, and the batch continues.
- **Summary contents:**
  - totals by category, team and priority
  - escalations by reason
  - Gemini fallback rate
  - Gemini-only count when the run was degraded
  - failed tickets
  - p50/p95 latency
  - cost per ticket and total cost

### 6.9 Failure handling (also the starting point for `docs/failure-modes.md`)

| Failure | Detection | Handling |
|---|---|---|
| Jev API down or rate-limited | `TypeSafeAPIError` after the SDK has retried | The run switches to Gemini-only classification and extraction, and `runs.degraded` is set to true |
| Gemini down | An exception from the Gemini client | Classification and Jev extraction still complete. The draft is skipped and the ticket is escalated with reason `llm_unavailable`. |
| Jev weak on Iraqi dialect or Arabizi | Low confidence or the option-order check disagrees | The cascade sends it to Gemini, and to a person if still uncertain. Accuracy is reported separately for these subsets. |
| Extraction invents a value | The span check fails | The value is set to `null`. The hallucination rate is measured. |
| Prompt injection in the ticket | The ticket is wrapped as untrusted data, the agent's tools are read-only, and the guardrails run | The draft guardrail fails and the ticket is escalated. Injection tickets are scored as their own subset. |
| Draft asks for an OTP or PIN | Regex plus the Jev Noul | The ticket is escalated with reason `draft_failed_guardrail` |
| Ticket contains several issues | The `multi_issue` Noul | The ticket is escalated with all candidate categories listed |
| Transaction not found or amount mismatch | `lookup.py` | The ticket is escalated with a note. The draft asks for the missing detail; it never asks for secrets. |

## 7. Data and evaluation

### 7.1 Generating synthetic data (`data/generation/`, fixed seeds)

**Base data, generated with `gemini-2.5-pro` from schemas, then validated in code:**
- about 40 customers, plus agents and merchants
- about 1,500 transactions over 60 days, including failed, pending and reversed ones
- 3 to 4 service incidents

**Tickets: labels come from code.**
1. A sampler in code produces a *scenario spec*: category, priority, channel, edge-case tags, the linked transaction (or none, or deliberately misstated details), and a date spread over 4 weeks.
2. Week 4 contains a planted spike in bill-payment failures that lines up with one incident.
3. `gemini-2.5-pro` writes the Iraqi-dialect ticket text from the spec.
4. Code checks that every gold extraction value really appears in the text. If one doesn't, the ticket is regenerated, or that gold value is set to `null`.

**Volume and spread:** about 300 tickets, stratified across the 12 categories.

**Edge-case tags:**

| Tag | Share of tickets |
|---|---|
| Arabizi (Arabic written in Latin letters) | ~10% |
| Arabic mixed with English | ~15% |
| More than one issue | ~8% |
| Missing details | ~15% |
| Prompt injection | ~3% |

Tags without a fixed share: typos or voice-note style, angry customers, fraud, amounts written in words, and Arabic-Indic digits.

**Knowledge base:** about 12 fictional policy and FAQ Markdown documents, each marked as synthetic.

**Hand check:** the team reads at least 50 tickets, scores realism from 1 to 5, and fixes or drops the bad ones. This is recorded in `docs/data-card.md`.

### 7.2 Split and how the test set is protected

1. **Split:** stratified by category with seed 42. `dev.jsonl` has 200 tickets; `test.jsonl` has 100.
2. **Hash first:** `test.sha256` is committed **before** any tuning starts.
3. **Tune on dev only:** all prompts, thresholds (`T_JEV`, `T_GEM`) and question wording are tuned on dev.
4. **Freeze, then test:** the test set is run once for each frozen configuration, and its results are committed.

### 7.3 Metrics (`eval/run_eval.py --mode {jev|gemini|cascade} --split {dev|test}`)

**Classification**
- Accuracy and macro-F1
- A confusion matrix, with a written discussion of the top 3 confusions
- Priority accuracy, both exact and within one level

**Flags**
- Precision and recall for each flag. Fraud recall is the headline number.

**Extraction**
- Exact match per field after normalisation
- Hallucination rate: a value was predicted where the gold value is `null`
- Missed-field rate

**Routing, lookup and escalation**
- Team accuracy and lookup accuracy
- Escalation rate
- Accuracy on tickets *not* escalated, plotted against coverage
- Escalation reasons broken down

**Calibration**
- A reliability diagram and ECE (expected calibration error) for Jev's confidence and for the cascade's final confidence

**Drafts**
- Guardrail pass rate and citation validity
- An LLM judge (`gemini-2.5-pro`) scores correctness, tone, dialect naturalness and actionability from 1 to 5
- The team rates 30 drafts by hand: "Would I send this with minor edits?"

**Operations**
- Throughput, p50/p95 latency, and cost per ticket for each mode

**Robustness slices**
- Arabizi, mixed language, multi-issue, injection, and missing details

**Output:** `eval/results/*.json` and `*.md`, which the Eval page renders.

**Known bias:** Gemini both generates the data and serves as one of the judges. This is disclosed, and the human ratings act as a counterweight.

## 9. Weekly pattern report (`reports/weekly.py`, stretch goal, in scope)

1. **Rising issues (code).**
   - Count tickets per ISO week for each category, team and flag.
   - An issue is **rising** when all of these hold:
     - this week's count is at least 1.5 times last week's
     - there are at least 5 tickets
     - a Poisson test gives p < 0.05
2. **Likely common cause (code plus Jev).**
   - Within each rising group, tickets are clustered by attributes of the transactions they matched: biller, agent_id, failure_reason, and type.
   - Clusters are checked for overlap with the time window of a `service_incident`.
   - A Jev Noul for each ticket asks: "Is `ticket_text` consistent with `incident.description`?"
3. **Narrative (Gemini).** A short summary in English with an Arabic version. It must cite counts and ticket IDs.
4. **Output.** An API endpoint, the UI page, and a Markdown export.

## 13. Risks

| Risk | Mitigation |
|---|---|
| Jev accuracy on Iraqi dialect is unknown (its primary training language is English) | The cascade fallback. Report results for each mode and each slice. If Jev underperforms, say so honestly. |
| Jev early-access rate limits change | Concurrency is capped at 20, the SDK retries, and the run falls back to degraded mode |
| Synthetic tickets don't sound real | Native-speaker hand check, edge-case tags, and dropping or regenerating bad tickets |
| Scope is too big for 1–2 weeks | Build order: pipeline and eval first, then the review UI, then the knowledge-base UI, then the weekly report |
| No user research | Accepted gap in the "Problem & impact" score. Can be revisited later. |

## 14. Implementation notes (added 2026-10-07, before implementation started)

The build follows the LangChain agent skills (`langchain-ai/langchain-skills`): `langchain-fundamentals`, `langgraph-decision-models`, `langchain-rag` and `langchain-dependencies`.

None of the following changes the architecture above. They decide which libraries implement it.

| Topic | Decision |
|---|---|
| Pipeline orchestration | The fixed stages in §6 become a **LangGraph `StateGraph`**. Each stage is one node. Routing between nodes (confident or not, which mode) is done by plain, testable Python functions. A batch runs with `graph.abatch(..., max_concurrency=PIPELINE_CONCURRENCY, return_exceptions=True)`. Per-node retries use LangGraph's `RetryPolicy`. This replaces the hand-written semaphore and retry loop described in §6.8. |
| Jev access | `langchain-typesafe` (`TypeSafeClassifier`, a LangChain `Runnable`) is used instead of the raw `typesafe-sdk`. It is alpha, so it is pinned to `0.0.1a3` and wrapped behind our own `Classifier` interface. |
| Gemini access | `langchain-google-genai`. Structured output uses `ChatGoogleGenerativeAI.with_structured_output(schema, method="json_schema", include_raw=True)`, so token usage is available for cost accounting. |
| RAG (Plan 3) | `GoogleGenerativeAIEmbeddings` plus `langchain-postgres` `PGVector` |
| Drafting agent (Plan 3) | `langchain.agents.create_agent` with `@tool` tools, middleware and a recursion limit |
| Jev question text | Instructions and criteria are plain strings built from the taxonomy (`Category.describe()`), not nested JSON. This is the safest shape for the alpha wrapper. |
| Jev priority | Read from the Score probability distribution (the most likely level), not by comparing `score` to an exact value. This follows the decision-models skill, which warns that `score` is an expected value. |
| `T_GEM` default | `0.66` instead of `0.67`, so that 2 of 3 Gemini samples agreeing passes. That was the intent of the original value. |
| Lookup status | The status `ambiguous` is added for when several transactions match. It escalates with reason `txn_ambiguous`. `date_mismatch` escalates too. |
| Schema management | `Base.metadata.create_all` through `support init-db` instead of Alembic. All data is synthetic and resettable, so migrations add no value for the hackathon. |
| CLI location | `backend/app/cli.py`, exposed as the `support` console script |
| Dev environment | The repo lives in WSL (`~/dev/zaincash-support`, Ubuntu-24.04), with Docker Engine running in WSL. Commits stay local; nothing is pushed. |
